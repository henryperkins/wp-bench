# WS1.0 Implementation Plan: Contracts and Reader

- Status: Design approved; implementation-ready
- Date: 2026-08-17; revised 2026-08-22
- Milestone: WS1.0, first of seven in workstream 1
- Specification: `../specs/2026-08-16-benchmark-integrity-design.md`

## Objective

Deliver the canonical schema, the canonical hashing primitive, and the reader,
with an additive compatibility corpus for every registered legacy structure.
Change no behavior: no run mode writes a different byte, and every existing
test passes untouched.

This milestone exists so the six milestones that follow have a contract to
write against and a reader to verify against, rather than discovering the
contract while rewriting the orchestrator.

## Scope

In scope:

1. `python/wp_bench/provenance.py`, containing only canonical hashing.
2. `python/wp_bench/schemas.py`, the full strict model set and version
   constants.
3. `python/wp_bench/results_reader.py`, `load_result_envelope()`,
   `load_result_envelopes()`, and `LegacyResultAdapter`.
4. An indexed fixture corpus for the four legacy structural families
   (single/reference, multi/skills, audit, and record-only streams), including
   every observed mode, format, and producer variant. Fixtures are generated
   from real runners rather than hand-written and are added, never replaced.
5. Tests for all of the above.

Explicitly out of scope, and deferred to the named milestone:

- Any change to `core.py`, `records.py`, `results_io.py`, `scoring.py`, or
  `selection.py`. Nothing writes the canonical format in WS1.0.
- Loader canonicalization, selection v2, and the selected catalog (WS1.1).
  WS1.0 defines the catalog's shape; it does not change what the loaders
  produce, so the local-versus-Hub `suite` divergence is still present in every
  fixture this milestone generates. That is deliberate: the fixtures must
  capture the harness as it is.
- Manifest emission, `RunArtifactWriter`, terminal-record ordering (WS1.2).
- Provenance *resolution*: git, Docker inspect, dataset digests, tree Merkle
  digests, the comparison allowlist (WS1.3). WS1.0 ships the hash function,
  not the things it will hash.
- Metric, completeness, and eligibility *computation* (WS1.4). Their models
  are defined here so the reader can carry legacy nulls through them.
- Bounded recovery and the coordinator (WS1.5).
- Any CLI surface.

The models defined but not yet produced are intentionally unexercised by
production code for the duration of this milestone. That is the cost of
contract-first sequencing, and it is bounded: WS1.2 begins writing them.

## Decision: use the `rfc8785` dependency

Approved 2026-08-22. Every JSON-derived digest in the specification is defined
over RFC 8785 JSON Canonicalization Scheme bytes. JCS is not "sorted keys with
no whitespace": it also fixes number formatting to ECMAScript
`Number::toString` and sorts object keys by UTF-16 code unit. Do not use
`orjson(OPT_SORT_KEYS)` or add an independent JCS implementation.

WS1.0 adds the exact pin `rfc8785==0.1.4` to `python/pyproject.toml` and commits
the corresponding `python/uv.lock` update. An exact direct pin is intentional:
the repository supports installations that do not consume the lockfile, and an
unreviewed serializer must not enter through such an install. Changing the
declared or resolved version is a digest-contract change that requires explicit
review and a clean run of the complete conformance suite before the declaration
and lockfile update land together.

The selected package is pure Python, has no runtime dependencies, supports
Python 3.8 and later, emits UTF-8 `bytes`, and raises on invalid JCS inputs. Its
Apache-2.0 license is accepted here through this project's
GPL-2.0-or-later grant: a combined distribution relies on the GPLv3-or-later
option, not GPLv2-only compatibility. A distribution that bundles the package
must preserve all attribution, license, and NOTICE material the Apache license
requires.

`python/wp_bench/provenance.py` is the only module allowed to import
`rfc8785`. Its public wrapper validates the input recursively before calling
the package. It accepts only concrete JSON value types (`None`, `bool`, `int`,
`float`, `str`, `list`, and `dict` with string keys), rejects integers outside
`-(2**53 - 1)` through `2**53 - 1`, rejects non-finite floats and lone Unicode
surrogates, and never coerces tuples, enums, paths, datetimes, decimals, bytes,
sets, mapping subclasses, sequence subclasses, or non-string keys. All
validation and upstream failures surface as the WP-Bench-owned
`CanonicalizationError`, with the upstream exception retained as its cause.

Conformance is independent of the dependency's own tests. Offline tests copy
the canonical example, UTF-16 property-order example, and complete Appendix B
number table from the immutable RFC 8785 publication. Appendix B values are
constructed from their 64-bit hexadecimal words with big-endian
`struct.unpack()`, rather than reparsed from the expected decimal spelling;
non-finite rows assert rejection. Python integers are tested separately at the
safe-domain boundaries, including the distinction that `2**53` as an `int` is
rejected while the Appendix B binary64 value at that magnitude remains a
`float`. The suite also covers recursive objects in arrays, exact escaping and
UTF-8 output, lone-surrogate rejection, signed zero, strict non-JSON rejection,
stable error translation, input-order independence, and WP-Bench-owned golden
digest vectors.

## Deliverables

### 1. `python/wp_bench/provenance.py`

WS1.0 creates the module named in the specification's architecture table, but
fills in only its hashing responsibility. WS1.3 adds redaction, dataset
snapshots, source-tree identity, and grader/runtime inspection.

```python
class CanonicalizationError(ValueError): ...

def canonical_json_bytes(value: Any) -> bytes
def canonical_sha256(value: Any) -> str
```

Contract:

- Serializes to RFC 8785 JCS bytes.
- Enforces the strict JSON tree and safe-number profile fixed by the decision
  above, including typed failures for NaN, infinity, out-of-range integers,
  lone surrogates, and non-JSON concrete types. A `Path`, `datetime`, tuple, or
  enum reaching a digest preimage is a loud failure, not a silent conversion.
- Translates dependency exceptions into the stable WP-Bench-owned
  `CanonicalizationError`; callers never depend on `rfc8785` exception types.
- Is the only hashing entry point for JSON-derived digests. `utils.sha256`
  stays as-is for text digests such as prompts and skill content.

### 2. `python/wp_bench/schemas.py`

Version constants exactly as specified: `RUN_MANIFEST_SCHEMA_VERSION`,
`RESULT_RECORD_SCHEMA_VERSION`, `RESULT_ENVELOPE_SCHEMA_VERSION`,
`RESULT_EVENT_SCHEMA_VERSION`, `SCORING_VERSION`,
`ELIGIBILITY_POLICY_VERSION`.

Models, all inheriting a strict base with `extra="forbid"`, following the
existing `config.py::StrictModel` convention:

| Group | Models |
|---|---|
| Manifest | `RunManifest`, `SelectionPlan`, `SelectedTest`, `RunUnit`, `ExternalUnitRef`, `TrialProtocol`, `RunPolicies`, `AuditPlan`, `AuditPlanTest`, `AuditPlanCandidate` |
| Provenance | `ProvenanceBlock`, `DatasetIdentity`, `ModelIdentity`, `HarnessIdentity`, `InterpreterIdentity`, `DependencyIdentity`, `GraderIdentity`, `RuntimeProfile`, `IsolationIdentity`, `EngineIdentity`, `SkillIdentity` |
| Record | `ResultRecord`, `RecordInput`, `RecordOutput`, `RecordOutcome`, `ExecutionScores`, `ExecutionAssessment`, `AuditAssessment`, `AuditCandidate`, `GraderResult`, `GraderPhase`, `CleanupResult`, `AttemptTelemetry`, `ProvenanceChecks` |
| Aggregate | `RunUnitAggregate`, `UnitCounts`, `Metric`, `UsageSummary`, `Eligibility` |
| Envelope | `ResultEnvelope`, `RunStatus`, `Completeness`, `SystemicFailure` |
| Events | `ManifestEvent`, `AttemptEvent`, `ResultEvent`, `RunTerminalEvent`, discriminated on `event_type` |

`IsolationIdentity` hangs off `RuntimeProfile`, not off `RunPolicies`, and its
canonical field names are authoritative. Any legacy isolation helper adapts
into that schema where its semantics are equivalent; an implementation symbol
never defines the contract.
`AuditPlan` is non-null exactly when `mode == exploit_audit`. `RunUnit` carries
a `source` discriminator, and a `sourced` unit names an `ExternalUnitRef`.
That reference carries `ref_id`, `source_run_id`, `source_unit_id`,
`source_semantic_envelope_sha256`, and the source
`contract_fingerprint_sha256`; resolution uses the normalized sealed semantic
digest after sibling deduplication, never a raw-file digest or path.
`Eligibility` carries the orthogonal `track` and `verification` axes plus the
`eligible` boolean, never a single fused enum.

Five shared invariants belong here rather than in the reader, because a
validator on the type is the only place they cannot be forgotten:

- `Metric`, carrying `value`, `numerator`, `denominator`,
  `denominator_kind`, with a validator enforcing that a zero denominator
  yields `value is None`. This single invariant is most of what the
  workstream is for; encode it once, in the type.
- `scores` and `diagnostic_scores` are mutually exclusive on `ResultRecord`,
  and `scores` is non-null exactly for outcomes `passed`, `failed`, and
  `diagnostic`.
- On `AuditAssessment`, `has_exploit` implies `audit_complete`. This is what
  keeps every audit numerator inside its denominator, so the model rejects a
  violating record rather than trusting the writer.
- `RunManifest` groups every non-null `pair_id` into exactly two units with the
  same actor and `trial_index`, variants `{baseline, skills}`, and sources
  consisting of either two executed units or one executed plus one sourced
  unit. Every sourced unit names exactly one external reference and no
  reference is orphaned.
- `require_supported_version(field, value, supported_major)`, so every
  reader path rejects unsupported majors identically instead of each
  call site inventing its own comparison.

Fields the later milestones populate (`provenance`, `config_sha256`,
`contract_fingerprint_sha256`, `prompt_template_sha256`, `metrics`,
`eligibility`) are nullable in the 1.0 and 3.0 contracts, per the staged
nullability rule in the spec's rollout. WS1.0 encodes that nullability; it does
not encode a `pending_milestone` producer, which arrives with the writer.

Nullable dimensions on `SelectedTest` are `X | None` with no defaults
omitted from serialization: the specification requires them present as JSON
`null`, never absent.
`SelectedTest` uses the exact field name `benchmark_definition_sha256`, and
both it and `SelectionPlan` use the exact fields, enum values, 64-hex digest
validation, and nullability frozen in the specification's
"Selection-plan fields and digest preimages" section. WS1.0 defines and tests
those shapes; WS1.1 is the first producer.

### 3. `python/wp_bench/results_reader.py`

```python
@dataclass(frozen=True)
class LoadedEnvelope:
    envelope: ResultEnvelope
    source: Path
    origin: ArtifactOrigin
    sealed: bool                           # complete terminal projection
    warnings: tuple[LoadWarning, ...]
    semantic_envelope_sha256: str | None   # None for open streams only

def load_result_envelope(path: Path) -> LoadedEnvelope
def load_result_envelopes(paths: Sequence[Path]) -> LoadResult
```

`ArtifactOrigin` is one of `canonical_json`, `canonical_jsonl`,
`canonical_partial`, `legacy_single`, `legacy_multi`, `legacy_audit`,
`legacy_records`.

Envelope equivalence and prefix supersession are relations *between* inputs,
so they cannot live behind a single-path function; the specification's
Legacy compatibility section now says so. `LoadResult` carries
`loaded: list[LoadedEnvelope]` and `failed: list[LoadFailure]`, because one
conflicting artifact must never fail an entire report.

Detection is by parsed structure rather than filename. Canonical namespace
recognition happens before version support is checked: a top-level
`schema_version`, or a first JSONL object whose `event_type` is `manifest`,
claims the canonical namespace. The reader then accepts a supported major or
fails that input as `unsupported_schema_major`; it never falls through to a
legacy adapter merely because the canonical version is newer.

For inputs outside the canonical namespace, the exact legacy discriminator
matrix is:

| Parsed shape | Result |
|---|---|
| Object with `metadata.mode == "exploit_audit"` | `legacy_audit`; this gate has precedence regardless of incidental `models` or `results` keys |
| Object with `metadata` and `models`, without `results`, and not audit | `legacy_multi` |
| Object with `metadata` and `results`, without `models`, and not audit | `legacy_single` |
| Non-empty JSONL stream whose parsed lines satisfy the registered legacy record predicate and whose first line is not a canonical manifest | `legacy_records` |
| Non-audit object with both `models` and `results`, or anything else | Per-input `LoadFailure` |

The predicates are exclusive after the audit precedence gate. No match or an
ambiguous shape yields a per-input `LoadFailure`; the reader never guesses.
`result_schema_version` is recorded but is never a legacy branch condition.
Every indexed fixture is a detection-matrix case, so a new producer structure
must either match exactly one registered predicate or add an explicit one.

`LegacyResultAdapter` normalizes in memory, never rewrites an input, and never
invents planned attempts, universe identity, provenance, or eligibility. It
preserves the lossless parsed source payload and unknown fields under
`extensions.legacy`. Every unknowable fact becomes null plus a stable warning:
`legacy_completeness_unverifiable`,
`legacy_provenance_unverifiable`, and one more this milestone will need,
`legacy_selection_unverifiable`, because `metadata.selected_test_ids` in the
evidence-baseline fixtures is derived from completed records and is therefore
the survivors, not the selection.

Sealed versus open is a content property, not a filename property: a
`.jsonl.partial` written past lifecycle step 7a carries a `run_terminal` event
and projects to a full envelope with a real `semantic_envelope_sha256`. Classify
by content. A validated final canonical JSON envelope is likewise sealed even
though it contains the terminal projection rather than an event; JSONL proves
the same state through `run_terminal`. The reachable-state table in the spec
is this module's test matrix.

Torn-line tolerance is asymmetric and must be tested as such: a malformed final
line is ignored only in a live `.jsonl.partial`, which is the only file
appended to in place; malformed content anywhere in a finished artifact, or
anywhere but the last line, is fatal.

### 4. Versioned legacy fixture corpus

`python/tests/fixtures/legacy/index.json` is the authoritative inventory. It
groups fixtures into four structural families while allowing multiple mode,
format, and producer variants in each family:

- single/reference payloads, including JSON and JSONL siblings;
- multi/skills payloads;
- exploit-audit payloads;
- record-only JSONL and truncated live streams.

Each artifact lives under `python/tests/fixtures/legacy/<fixture-id>/` and is
additive. An index entry contains:

- `fixture_id`, immutable `artifact_path`, `family`, `mode`, `format`, and
  expected `ArtifactOrigin`;
- the full `source_commit`, stable `source_observation_id`, and deterministic
  `generator_profile` version;
- `artifact_sha256` over the original bytes;
- `structural_fingerprint_algorithm` and `structural_fingerprint_sha256`;
- `torn_final_line_dropped`, true only for the tolerated live-partial case;
- the exact discriminator expected to match;
- required legacy warnings and the expected adapter outcome.

For algorithm `wp-bench-legacy-structure/1`, define `shape(value)` exactly as
follows: null, boolean, number, and string become `["null"]`, `["boolean"]`,
`["number"]`, and `["string"]`; an object becomes
`["object", [[key, shape(child)], ...]]` with pairs in RFC 8785 object-key
order; and an array becomes `["array", [[child_shape, count], ...]]`, a
run-length-encoded multiset ordered by `canonical_json_bytes(child_shape)`.
JSON uses `shape(parsed_value)`. JSONL uses `shape(array_of_parsed_lines)`.
`canonical_sha256()` hashes
`["wp-bench-legacy-structure", 1, recursive_shape]`. This retains nested
key/type correlation and multiplicity while intentionally ignoring values and
array order. The byte digest separately detects value or ordering drift.

For a live `.jsonl.partial` only, the reader may drop at most one malformed
final line under the torn-line rule before it constructs `recursive_shape`.
`artifact_sha256` still covers every original byte, including the malformed
tail, and the index sets `torn_final_line_dropped=true`. Finished artifacts,
earlier malformed lines, or an empty valid prefix fail and receive no adapted
shape. This vector is normative:

```text
raw_utf8 = "{\"test_id\":\"e-one\"}\n{\"test_id\":"
artifact_sha256 = 3c6a2d16fb76b84ad813d827b3fb3c62c933145f85e1f52eb65111b8c074df55
recursive_shape = ["array",[[["object",[["test_id",["string"]]]],1]]]
structural_fingerprint_sha256 = 2bb82abd3856ef2150eeb115164dde937ffb6451984d885a20ba04314270fc31
```

Each evidence-source record declares the full `source_commit`, generator
profile, and complete `expected_observations` array. Each expected observation
has a stable `source_observation_id`, mode, producer variant, and format. The
index and evidence manifest form a bidirectional one-to-one join on
`(source_commit, source_observation_id)`: every expected observation has
exactly one fixture entry, and every historical fixture entry names exactly
one declared observation. Per-source expected counts are derived from that
array and checked, never inferred later from whatever files happen to exist.

The stable maintainer interface for a later writer-changing milestone is:

```bash
python python/tests/fixtures/generate_legacy.py append-new \
  --source-commit "<full immutable commit SHA>" \
  --generator-profile legacy-generator/1
```

`append-new` materializes that exact commit, runs the complete fixed profile,
and appends evidence-source/index entries plus immutable fixture paths only for
previously unregistered structural/byte pairs. It is a no-op when every pair is
already registered and fails without mutation on an unreachable commit,
missing expected output, nondeterminism, or any non-drift generator error. It
never rewrites an existing byte, path, digest, observation, or annotation.

The maintainer generator materializes every listed source in a detached
temporary worktree and records one fixture observation per emitted artifact,
even when two sources produce identical bytes. Failure to materialize an
initial source blocks implementation readiness rather than silently shrinking
the corpus. Once checked in, historical artifacts are validated only from
their immutable bytes, index metadata, and digests; ordinary CI never
regenerates them through live writer code. A source commit becoming unreachable
later does not invalidate its checked-in evidence.

An existing fixture is never overwritten to accept writer drift. A new
`(structural_fingerprint_sha256, artifact_sha256)` observation adds a new entry
with its producer commit. If two merge orders produce distinct deterministic
artifacts, both remain. A generator defect does not permit replacement: the
original entry, path, and bytes stay unchanged; a separate additive annotation
records the defect, and corrected output receives a new fixture ID, path, and
entry. The index's append-only `annotations` records carry `annotation_id`,
`target_fixture_id`, `kind`, `reason`, and `recorded_commit`; annotating history
never mutates the target fixture entry.

## Merge-order-independent integration policy

The implementation has two capability checkpoints, not prescribed pull
request identities. Checkpoint A provides canonical hashing and schema APIs.
Checkpoint B provides the reader and corpus and therefore executes against a
base containing A. They may be bundled in one change, stacked, or merged as
separate changes; no checkpoint names an external branch or waits for an
unrelated merge.

Separately, CI probes the checked-out legacy writers with the fixed profile in
a temporary directory. The probe must emit the complete expected observation
set for its profile, and each output must match a registered
fingerprint/digest pair. A missing expected output fails as producer drift. An
unknown pair fails with an instruction to append an evidence-source record and
new fixture entry; neither case rewrites or regenerates a historical fixture.
Reader tests load every indexed entry on every commit. Consequently a
writer-changing branch may land before or after the reader/corpus checkpoint,
between its commits, or not at all without invalidating or erasing any
previously supported structure.

Legacy detection is structural and must never branch on
`result_schema_version`. The versioned recursive fingerprint is the
structure-drift observable: it catches nested additions, removals, correlated
type changes, and multiplicity changes that a top-level key-set check would
miss. The byte digest catches all other deterministic drift. Any canonical
writer field-set change still requires its schema-version bump in the same
change.

## Risks

- **The schema is written before anything produces it.** Mitigated by the
  representability check, which is the closest thing to a writer that exists
  at this point. Residual risk lands in WS1.2 and is accepted.
- **Fixture growth.** The corpus grows whenever a deterministic producer
  structure or value contract changes. That is intentional compatibility
  history. The index, byte digests, and additive-only rule make growth explicit
  and prevent the newest snapshot from erasing an older reader obligation.
- **Dead code for one milestone.** `Eligibility`, `Metric`, and most of
  `ProvenanceBlock` have no producer until WS1.3 and WS1.4. Accepted
  deliberately: the alternative is defining contracts inside the change that
  also rewrites the orchestrator.
- **JCS dependency drift.** `rfc8785` is a beta, single-maintainer dependency
  governing persistent digest bytes. The exact direct pin, exact lock,
  one-module wrapper, immutable RFC vectors, WP-Bench golden vectors, and
  explicit declaration-and-lock review rule prevent an ordinary dependency
  refresh or unlocked install from silently changing the digest contract.
- **License floor.** Apache-2.0 is compatible through GPLv3, not GPLv2-only.
  The repository remains GPL-2.0-or-later, but any combined distribution must
  select GPLv3-or-later and preserve required Apache attribution. A future
  GPLv2-only distribution requirement would reopen this decision.
